## 2. 문제 정의

### 2-1. 시장 현황

국내 민간 보험 가입자는 전체 인구의 **약 75%** 수준이며, 1인당 평균 3.2개의 보험을 보유하고 있습니다. 그럼에도 실제 보험금 청구율은 현저히 낮습니다.

> **연간 미청구 보험금 추정액: 2조 원 이상**  
> — 금융감독원 보험 소비자 실태조사 참고

### 2-2. 미청구의 3가지 원인

```
① 복잡성  — 수백 페이지 약관, 어려운 법률 용어
② 귀찮음  — 소액(1~5만원)이라 청구 절차가 더 번거로움
③ 무지    — 특약 존재 자체를 모르거나 보장 범위 불명확
```

### 2-3. 기존 방식의 한계

| 기존 방법 | 문제점 |
|-----------|--------|
| 보험사 앱 | 내 보험만 확인 가능, 비교 불가 |
| 콜센터 상담 | 평균 대기 30분 이상 |
| 보험 설계사 | 영업 목적 개입, 신뢰도 낮음 |
| 직접 약관 검색 | 수백 페이지 중 해당 조항 찾기 불가 |

## 3. 솔루션

### InsurRX의 접근 방식

```
처방전/영수증 사진 1장
        ↓
GPT-4o Vision OCR
(한글·영문·숫자 자동 인식)
        ↓
상병코드 · 약품명 · 금액 구조화
        ↓
Pinecone 벡터 DB 약관 검색
(의미 기반 RAG, 1,358개 조항)
        ↓
GPT-4o 보상 분석
        ↓
청구 가능 여부 + 예상 금액 + 약관 근거
      [목표 3초 — 실측은 14장 지표로 검증]
```

### 핵심 차별점

| 항목 | InsurRX | 기존 서비스 |
|------|---------|------------|
| 분석 단위 | 질병코드·약품 단위 정밀 분석 | 진단명 키워드 매칭 |
| 면책 조항 | AI가 비급여·선천성 질환 사전 필터링 | 수동 확인 필요 |
| 약관 근거 | 적용된 조항 원문 인용 | 결과만 제공 |
| 다보험 비교 | 보유 보험 전체 동시 매칭 | 단일 보험사 |
| 속도 | 3초 이내 응답 | 수 분~수십 분 |

## 4. 핵심 기능

### 4-1. Vision OCR

- **엔진**: GPT-4o Vision (gpt-4o-mini)
- **인식 대상**: 진료비 영수증, 처방전, 약품 봉투
- **추출 항목**: 병원명, 진료과, 상병코드(ICD), 처방일, 본인부담금, 약품명·용량·일수, 비급여 항목
- **지원 포맷**: JPEG, PNG, WEBP, HEIC(자동 변환)
- **2단계 파싱**: 정규식 1차 추출 → 누락 시 GPT-4o-mini LLM 보완

### 4-2. RAG 보상 분석

- **Vector DB**: Pinecone (AWS us-east-1, 1,358개 벡터)
- **임베딩**: OpenAI text-embedding-3-small (dim=1536)
- **보유 약관 4종**:

| 약관 | 보험사 | 종류 | 벡터 수 |
|------|--------|------|---------|
| Hi2204 | 현대해상 | 실손의료보험 | 약 350개 |
| Hi2401 | 현대해상 | 암보험 정액형 | 약 480개 |
| My아이플러스 | 삼성화재 | 어린이보험 | 약 390개 |
| 갱신형 2501 | AXA | 치아보험 | 약 138개 |

- **LLM**: GPT-4o (보상 판단·금액 계산·약관 해석)
- **출력**: 청구 가능 여부, 예상 보상 금액, 계산 내역, 약관 조항 원문 인용, AI 신뢰도
- **추적 정보 저장** *(v1.1)*: 결과마다 사용 모델명, 프롬프트 버전(내용 해시), 처리 시간(ms), 유입 채널(웹/카카오)을 기록합니다. 같은 입력의 결과가 달라졌을 때 원인을 확인할 수 있습니다.
- **개인 보험증권 RAG** *(v1.0 이후 추가)*: 로그인 사용자가 업로드한 보험증권(PDF/이미지)을 사용자별 네임스페이스에 임베딩해 공개 약관과 함께 검색합니다.

### 4-3. Waitlist 이메일 수집

- Railway PostgreSQL 저장 (중복 방지)
- Formspree 폴백 (API 장애 시 자동 전환)
- 선착순 1,000명 → 베타 출시 알림

### 4-4. 카카오톡 채널

- 채널 URL: https://pf.kakao.com/_xmxfjxjX
- 스킬 서버 구현 완료 *(v1.0 이후)*: `POST /api/v1/kakao/skill` — 이미지 수신 → 약관 선택 → 비동기 OCR+RAG → 결과 확인. 카카오 5초 응답 제한에 맞춰 분석은 백그라운드에서 처리합니다.
- 결과 카드에 추정치 고지 문구와 "결과가 다를 때" 안내 버튼을 넣었습니다 *(v1.1)*.

## 6. 사용자 시나리오

### 메인 플로우 (6단계)

```
STEP 1  사진 입력 방법 선택
        [📷 카메라 촬영] 또는 [🖼️ 갤러리 선택]

STEP 2  이미지 미리보기 확인
        → "AI 분석 시작" 클릭

STEP 3  OCR 분석 중 (평균 3~5초)
        GPT-4o Vision이 처방전 텍스트 추출

STEP 4  인식 결과 확인
        병원명 · 상병코드 · 약품 · 본인부담금 표시
        → "보상 분석 받기" 클릭

STEP 5  보험 선택
        가입 보험 체크박스 선택 (복수 선택 가능)
        → "분석 시작" 클릭

STEP 6  RAG 분석 중 (평균 5~10초)
        Pinecone 벡터 검색 + GPT-4o 보상 판단

STEP 7  분석 결과 리포트
        · ✅ 청구 가능 / ❌ 청구 어려움
        · 예상 보상 금액 (₩ XX,XXX)
        · 계산 내역 (본인부담금 - 공제액)
        · 적용 약관 조항 + 원문 인용
        · AI 신뢰도 %
        · ⚠️ 추정치 고지: "최종 지급 여부와 금액은 보험사 심사로 결정"   (v1.1)
        · "실제 지급 결과가 예상과 다르다면?" 안내 (13장 절차)        (v1.1)
```

출력:  is_claimable=true
       estimated_payout=18,500원

| 가격 | Waitlist 설문 `paid_intent`·`price_range` 집계 + 실제 전환율 | 설문 응답과 실제 전환의 차이 확인 |

결제 연동은 CBT 이후에 붙이며, 그 전에는 `users.plan`, 월 사용량 집계, 한도 초과 안내 화면만 준비합니다.

## 13. 예상 금액 산정 근거와 차이 발생 시 안내

### 13-1. 현재 산정 방식과 한계

| 항목 | 현재 | 한계 |
|------|------|------|
| 금액 계산 | LLM(GPT-4o)이 약관 조항과 영수증을 보고 직접 산출 | 같은 입력에도 결과가 달라질 수 있음 |
| 공제 규칙 | 프롬프트에 "의원 1만원, 약국 8천원" 한 가지만 명시 | 실손은 가입 세대(1~4세대)에 따라 자기부담률·최소공제액이 다름 |
| 계산 내역 | `breakdown` — 형식이 정해지지 않은 항목별 금액 | 항목 이름이 매번 다를 수 있음 |
| 신뢰도 | LLM이 스스로 매긴 값 | 실제 정확도와 맞춰 보정되지 않음 |
| 추적성 | ✅ v1.1부터 모델명·프롬프트 버전·처리 시간 저장 | 참조 약관 데이터 버전은 미기록 |

### 13-2. 사용자 고지 (v1.1 적용)

웹 랜딩, 회원 대시보드(결과·이력 상세), 카카오 결과 카드에 같은 문구를 표시합니다.

> ⚠️ 이 금액은 약관과 영수증을 바탕으로 AI가 계산한 **추정치**입니다. 최종 지급 여부와 금액은 **보험사 심사**로 결정됩니다. 실손보험은 가입 시기(1~4세대)에 따라 공제액과 자기부담률이 달라 실제 금액과 차이가 날 수 있습니다.

### 13-3. 산정 방식 개선 계획 — 판정과 계산의 분리

```
[현재]  영수증 + 약관 ──▶ LLM ──▶ 보장 여부 + 금액

[개선]  영수증 + 약관 ──▶ LLM ──▶ 보장 여부 + 적용 조항 + 급여/비급여 구분
                                        │
        가입 세대·병원 등급 ──▶ 규칙 엔진 ──▶ 금액 + 산정식
                                (세대별 자기부담률·최소공제 표)
```

- 금액은 규칙 엔진이 계산하므로 같은 입력이면 항상 같은 결과가 나오고, `본인부담금 − 공제액 = 예상 지급액` 형태로 산정식을 보여줄 수 있습니다.
- 가입 세대를 모르면 세대별 금액 **범위**로 표시합니다.

### 13-4. 실제 결과와 차이가 날 때의 안내 절차 (v1.1 적용)

결과 화면의 "실제 지급 결과가 예상과 다르다면?"(카카오: "결과가 다를 때" 버튼)에서 안내합니다.

| 단계 | 내용 |
|------|------|
| ① 차이 원인 확인 | 실손 가입 세대별 공제액·자기부담률 / 비급여 항목 포함 여부 / 다른 보험과의 중복 보장(비례 보상) / 청구 서류 누락 |
| ② 보험사 재심사 요청 | 고객센터에 지급 산출 내역 요청. 진료비 영수증·진료비 세부내역서·처방전(약제비)·필요 시 진단서를 보완해 재청구 |
| ③ 분쟁조정 신청 | 금융감독원 ☎ 1332 / e-금융민원센터(www.fcsc.kr). 보험금 청구권 소멸시효(3년) 안내 |
| ④ 서비스 개선 반영 *(예정)* | 사용자가 입력한 실제 지급 결과를 관리자가 검토해 약관 데이터·프롬프트 개선에 반영 |

④를 위해 분석 결과에 실제 지급 결과 입력 기능을 추가합니다 (`actual_payout`, `actual_status`, `feedback_at`).

## 14. 사용 반응 지표와 검증 계획

### 14-1. 현재 측정 가능한 것과 없는 것

| 측정 가능 | 측정 불가 (보완 필요) |
|-----------|----------------------|
| 가입·로그인 수 (관리자 오늘 대시보드) | OCR 요청·실패·재촬영 등 단계별 이탈 — `/upload`가 DB에 기록하지 않음 |
| 누적 분석 수, 청구 가능 비율 | 비로그인 조회 수, 재방문 |
| 분석별 처리 시간·모델·채널 *(v1.1)* | 실제 지급액과의 차이 |
| Waitlist 설문 — 사용 의향·지불 의향·희망 가격 | 실제 유료 전환 |

### 14-2. 사용 이벤트 수집 (예정)

`usage_events` 테이블(익명 세션 ID 포함)에 다음 흐름을 기록합니다.

```
ocr_requested → ocr_success / ocr_fail → ocr_retry
             → analyze_requested → result_viewed → feedback_submitted
```

### 14-3. CBT 핵심 지표

| 지표 | 정의 | CBT 목표 (제안) |
|------|------|-----------------|
| OCR 성공률 | ocr_success / ocr_requested | ≥ 90% |
| 분석 전환율 | analyze / ocr_success | ≥ 60% |
| 응답 시간 P90 | OCR + RAG 총 소요 | 목표 3초 대비 실측 기록 |
| 금액 오차율 | \|예상 − 실제\| / 실제 (피드백 건) | 중앙값 ≤ 10% |
| 판정 일치율 | 청구 가능 판정 = 실제 지급 여부 | ≥ 85% |
| 재방문율 | 7일 내 2회 이상 분석한 사용자 비율 | 측정 후 설정 |
| 월 사용 횟수 분포 | 사용자별 월 분석 수 | 무료 한도 결정 근거 (8장) |

### 14-4. 금액 정확도 검증 데이터셋

- 실제 영수증과 실제 지급 결과가 있는 30~50건(CBT 피드백 + 팀 보유분)으로 회귀 테스트를 만듭니다.
- 프롬프트·모델·약관 데이터를 바꿀 때마다 오차율과 판정 일치율을 기록합니다. 프롬프트 버전은 v1.1부터 결과에 저장되므로 버전별 비교가 가능합니다.
